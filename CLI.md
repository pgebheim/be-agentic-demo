# CLI — `chain`, the front door to the chain

## Why

Today the chain is libraries (`types`, `util`) with no way to *touch* it. As the
node, consensus, indexer, and explorer land, they need one human-facing front
door: run a piece, submit a transaction, inspect a block, tail the live head.

`chain` is that front door — a single umbrella binary that **grows one
subcommand group per milestone**. It starts now as a thin inspector over the
pure Milestone-0 foundations, so it exists and is useful before the node does,
and it never gets ahead of the spec's foundations-first build order.

## Non-goals

- Not a second home for domain logic. Command handlers are a thin presentation
  layer that *call into* the library crates. Logic stays in `types` / `util` /
  `store` / … so those layers remain independently unit-testable.
- Not a rewrite of the spec's architecture. The spec's `node` and `validator`
  are still real programs — here they are reachable as `chain node` and
  `chain validator` subcommands rather than separate binaries (one tool to
  learn, one `--help` to read).

## Shape

One binary, `chain`, from a new `crates/cli`, built with **clap v4 (derive)**.
Subcommands are grouped by concern and light up as the milestone they depend on
is built:

```
chain
├── hash        <data> | --file <path>          # M0 · SHA-256 via util
├── block
│   └── build   --tx from:to:amount ...          # M0 · construct + digest a block
├── verify      <chain.json>                     # M0 · check every parent_digest link
├── genesis                                       # M0 (after T3) · print deterministic genesis
├── node
│   ├── run     [--interval 3s]                  # M1 · the CHN-3 mint loop
│   └── head                                      # M1 · print current head
├── validator
│   └── run     --id N                           # M3 · boot one validator
├── cluster
│   └── up      --validators 4                   # M3 · local BFT cluster
├── query       latest | height N | digest D     # M4 · read the indexer REST API
├── tx
│   └── submit  --from --to --amount             # M4 · push a transaction
├── watch                                         # M4 · live tail of the WS finalization stream
└── completions zsh | bash | fish                # shell completions
```

### Available today (Milestone 0 — pure, no node required)

These run against the code that already exists, so the CLI is real from day one:

- **`chain hash <data>`** / **`--file <path>`** — SHA-256 digest via `util::digest`.
  A trivial-but-real command that exercises the foundation and gives the tool a
  reason to exist immediately.
- **`chain block build --tx aa:bb:5 --tx cc:dd:9`** — build a `Block` from the
  given transactions, print it, and print its computed digest. Demonstrates the
  T1 + T2 link.
- **`chain verify <chain.json>`** — read a JSON array of blocks and confirm each
  block's `parent_digest` equals its predecessor's digest. The first command
  that treats the data as a *chain*.
- **`chain genesis`** — print the deterministic genesis block (lands with T3);
  running it twice proves determinism.

### Grows with the milestones

| Milestone | Subcommands | Depends on |
|-----------|-------------|------------|
| M1 · chain that grows | `node run`, `node head` | CHN-1/2/3 store + append |
| M3 · validator node   | `validator run`, `cluster up` | consensus core (M2) |
| M4 · indexer          | `query {latest,height,digest}`, `tx submit`, `watch` | indexer REST + WS |

`chain watch` is the crowd-pleaser: subscribe to the indexer's finalization
WebSocket and tail finalized blocks live in the terminal — a mini block explorer
before the web explorer (M5) exists.

## Cross-cutting "awesome"

- **`--format {pretty|json|compact}`** (global). `pretty` is colored and aligned;
  `json` makes every command pipe cleanly into `jq`. Machine output is a
  first-class citizen, not an afterthought.
- **Colored, aligned pretty output** — heights, digests (truncated with a
  `abcd…1234` middle-ellipsis), and tx counts laid out like a terminal explorer.
- **Shell completions** generated by clap (`chain completions zsh`).
- **Stable exit codes** — `0` success, `1` usage error, `2` verification failure
  — so `chain verify` is usable as a CI gate.

## Crate layout

```
crates/cli/
  Cargo.toml        # bin name "chain"; deps: clap, types, util, (later) store/node/indexer-client
  src/
    main.rs         # clap parse → dispatch
    cmd/
      hash.rs
      block.rs
      verify.rs
      …             # one module per subcommand group; each is thin
    format.rs       # pretty/json/compact rendering shared by all commands
  tests/
    cli.rs          # assert_cmd end-to-end: run the binary, assert stdout/exit code
```

Handlers take parsed args and a `Format`, call into the library crates, and
render. No domain logic in `cli`. This keeps the spec's layering intact:
`types → chain rules → consensus → indexer → explorer`, with the CLI a
*consumer* of each layer.

Serialization: `block build` / `verify` / `query` exchange blocks as JSON. That
implies a `serde` derive on `types::Block` / `Transaction` — a small, additive
change to Milestone 0 that the indexer (M4) will need anyway, so the CLI pulls
it forward rather than inventing a parallel format.

## Build order for the CLI itself

Foundations-first, matching the spec's ethos:

1. **CLI-1 · Scaffold + `hash`.** `crates/cli`, clap wired, `chain hash` working,
   `--format` plumbed, one `assert_cmd` test. Proves the skeleton.
2. **CLI-2 · `block build` + `verify`.** Needs `serde` on `types`. The first
   commands that manipulate real chain data.
3. **CLI-3 · `genesis`.** Follows T3.
4. Then one thin ticket per milestone as `node` / `validator` / `query` / `watch`
   become buildable.

## Success criteria

1. `cargo build` produces a `chain` binary; `cargo test -p cli` is green.
2. `chain hash hello` prints the known SHA-256; `chain verify` exits non-zero on
   a broken link.
3. Every command supports `--format json` and round-trips through `jq`.
