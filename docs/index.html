02

Learning 02 · specs, not steering

Stop guiding.Start spec-ing.

The instinct is to steer the agent turn by turn. It works when the work is narrow — and breaks the moment it goes wide.

Guiding

You hold the plan.

Every turn needs you. The context lives in your head and dies with the session.

Spec-ing

The spec holds the plan.

Iterate a SPEC → a reviewable execution plan → trusted runs. You review the plan and the result, not every keystroke.

Guiding, up close

It's easy to become the loop.

what that actually looks like

  • cpcopy-paste snippets between windows
  • F5refresh the page… again
  • runrestart the demo to reproduce it
  • tailopen test-output.log and squint
  • ↑↵re-run the last command, tweak, repeat

Every turn routes through you. It works — until two of these run at once, and there's one of you.

Spec-ing, up close

So step out of it.

You touch it twice — the spec going in, the review coming out. The turning is the machine's job now, and it scales past one of you.

rig-task · the steps

What every ticket actually runs.

Load the spec

From the ticket (or an ad-hoc description). Guard first: is this an epic child that should stack, not land on trunk?

Spec review

Architect + QA sanity-check the plan — before a line of code.

RED

gate

Write the failing test first — and it must fail for the right reason. No test that passes on arrival.

GREEN

Minimum code to pass; loop up to 3× until the whole suite is green.

Refactor

Tidy while green — no new behavior. Skip if it's already clean.

Self-review

gate

Fresh-eyes pass against the review catalog; fix every P0/P1 before opening.

Open the PR

Link the ticket, move it to In Review. Never auto-merges unless you asked it to.

Review-bot loop

Drive the bot until the PR is clean, or hand back to a human.

Every ticket runs this. The gates — a test that must fail first, a review that must pass — are why you can trust the ones you didn't watch.

Higher level

One ticket. Then a whole epic. Then hands-off.

Basic
rig-plan + rig-task

Break the spec into tickets, then take each unit end-to-end — RED → GREEN → review gate → PR. What you just watched.

Higher
rig-epic

For work that interleaves: many tickets on one shared integration branch, run in dependency order, reviewed as a combined diff across three lenses, then squashed to the trunk as a single PR. Same gates — one level up.

Next
rig-loop

Close it entirely: a dispatcher watches the board, picks up the next ready ticket, builds and lands it — and repeats until the backlog is dry. Move a card; walk away.

rig-epic · the steps

How an epic actually runs.

Plan

Decompose the feature into a parent + children on the board (native sub-issues), in dependency order. You review the plan, not the code.

Start

Cut one shared integration branch off the trunk; move the parent to In Progress.

Spec review — all children

gate

Once, before any code: architect + QA read every child's spec together, then either proceed — with per-child direction the coders follow — or halt. On --advisor a Fable decides it unattended, so a kicked-off epic never parks here.

Run

gated ×N

Each child is a full rig-task — its own RED → GREEN → review gate — landed in dependency order and stacked on the branch.

Combined review

gate

Fresh-context, three-lens review of the integrated diff — the shape as a whole, not the pieces you already gated.

Finish

your call

Squash the branch to the trunk as one reviewed PR. Never auto-merges the trunk without your opt-in.

Prune

Tidy the integration branch and the per-child worktrees.

Every child carries the ticket-level gates; the epic adds one more — a review of the whole before it touches the trunk. Same rigor, one level up.

What's next

Spec'd work is measurable work.

Once the flow is specs → plans → gated runs, every run emits the same shape of evidence: did the tests pass, did the review gate hold, did it meet the acceptance criteria. That's exactly what an eval feeds on.

  • 01The real tickets you already run become the eval suite — your work is the benchmark.
  • 02Score a change to a skill or a prompt against it before you ship it.
  • 03Let the system tune toward what actually passed — self-improvement with a scoreboard.

You can't eval "vibes." You can eval a spec with acceptance criteria and a gate.
